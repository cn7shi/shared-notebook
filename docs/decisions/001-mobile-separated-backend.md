# ADR-001：移动端客户端与稳定业务后端分离

日期：2026-10-05
状态：架构方向已根据用户要求确定；具体服务端框架为实施提案。

## 背景

产品以 Android / iOS 为核心，页面和交互预计频繁修改。
用户要求数据操作不与前台强绑定，并为三个产品分别建立仓库。

## 决定

使用 Flutter / Dart 实现移动客户端。
采用独立 HTTP 后端和 OpenAPI 契约，将持久化、权限和核心业务规则放在后端。
客户端内部进一步分离页面、状态和数据接口。
每个产品使用自己的仓库；mobile 与 server 分别构建和部署。

首选服务端方案为 NestJS / TypeScript + PostgreSQL。
NestJS 的模块结构适合隔离业务能力，OpenAPI 支持便于维护跨语言接口；
PostgreSQL 的事务、唯一约束和外键用于保证数据关系。
框架可以替换，公开契约与业务规则不应随替换而无意变化。

## 考虑过的方案

- React 网页优先：符合此前浏览器优先的假设，但该假设已被移动端优先更正。
- Flutter 页面直接操作云数据库：早期接入简单，但会让数据库结构和业务规则进入页面。
- 每产品一个客户端仓库加一个服务端仓库：可行，但用户要求三个仓库，
  当前按每产品同仓分目录即可保留独立发布边界。
- 过早拆分多个微服务：当前三个产品还在验证，先用各自模块化后端减少部署复杂度。

## 原因

页面可以换布局、导航与组件，只要调用相同业务接口就保留数据行为。
同一个服务端可以验证来自不同版本 App 的请求。
业务测试可以在没有手机界面时运行，并直接验证归属、并发和历史数据约束。

## 代价

需要维护客户端与服务端两套运行环境，处理网络失败和版本兼容。
Flutter 能共享主要代码，仍需分别验证 Android 和 iOS 的平台行为。
本地草稿与服务端状态的合并需要显式规则，不能假设天然同步。

## 验证

- 服务端在没有 Flutter 的情况下独立启动并完成接口测试。
- 页面重排不改变 OpenAPI 契约及服务端业务测试。
- 旧版契约请求在兼容变更后仍通过。
- 多用户隔离、重复请求、并发修改和网络重试均有针对性验证。
